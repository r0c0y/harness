# Problem framing

1. Separate the user's observed symptom from their desired outcome.
2. Identify who or what is affected, the current behavior, and the expected behavior using available evidence.
3. Mark facts, assumptions, constraints, and unknowns separately.
4. Define a narrow success condition that can be checked.
5. If a missing decision changes scope or architecture, ask about that decision; otherwise proceed with a stated, reversible assumption.

Do not smuggle a preferred implementation into the problem statement. Keep the existing interface and workflow unless the request says otherwise.
